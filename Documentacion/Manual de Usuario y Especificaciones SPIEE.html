Documento ejecutivo de referencia para encargados administrativos, operativos y de supervisión

Institución: Universidad Técnica Nacional

Propósito: Presentar de forma clara, formal y ejecutiva el funcionamiento del sistema, sus módulos, reglas de operación y especificaciones clave.

1. Resumen Ejecutivo

SPIEE es la plataforma institucional utilizada para controlar activos, insumos, solicitudes de préstamo, validación documental y gestión de usuarios dentro del entorno de la Escuela de Ingeniería Electrónica. Su aporte principal es consolidar en un solo sistema los procesos críticos de operación del laboratorio, fortaleciendo el orden administrativo, la trazabilidad y la toma de decisiones.

Desde una perspectiva ejecutiva, el sistema permite saber qué recursos existen, quién los solicita, en qué estado se encuentran, qué usuarios están habilitados para operar y qué condiciones académicas o administrativas deben cumplirse antes de aprobar un préstamo. Esto reduce riesgos de pérdida de control, mejora la supervisión y aporta evidencia para auditoría y seguimiento institucional.

2. Introducción

El sistema SPIEE fue desarrollado para apoyar la administración integral del inventario, los préstamos y el control de usuarios de la Escuela de Ingeniería Electrónica. Su objetivo principal es centralizar en una sola plataforma los procesos de registro, consulta, solicitud, aprobación, entrega, devolución y seguimiento de activos e insumos, reduciendo la dependencia de controles manuales y mejorando la trazabilidad institucional.

Este manual está orientado a encargados administrativos, personal operador, responsables de laboratorio y personas con funciones de supervisión. Por esa razón, el documento no se limita a describir pantallas, sino que también explica la lógica operativa del sistema, los estados válidos de los registros, las reglas de negocio que se aplican de forma automática y las recomendaciones para un uso correcto.

3. Objetivo del sistema

SPIEE permite gestionar de manera ordenada los recursos del laboratorio y controlar quién solicita, utiliza y devuelve los bienes institucionales. Además, integra controles sobre periodos académicos, validación de boletas estudiantiles, aprobación de docentes, lista de espera, reportes y permisos diferenciados por rol.

En términos prácticos, el sistema resuelve cinco necesidades clave:
  1. Controlar el inventario de activos e insumos.
  2. Registrar solicitudes y préstamos con trazabilidad.
  3. Restringir accesos según el tipo de usuario.
  4. Dar seguimiento a boletas, periodos académicos y estados de matrícula.
  5. Producir información útil para la toma de decisiones y la supervisión del laboratorio.

4. Alcance funcional

De acuerdo con la estructura actual del proyecto, el sistema cubre los siguientes módulos operativos:

  • Acceso al sistema e inicio de sesión.
  • Registro de usuarios y carga de boleta PDF.
  • Gestión de usuarios, roles, permisos y estados.
  • Gestión de activos del laboratorio.
  • Gestión de insumos consumibles.
  • Creación y seguimiento de solicitudes de préstamo.
  • Control de lista de espera.
  • Gestión de cuatrimestre y validación documental.
  • Perfil de usuario, notificaciones y seguimiento personal.
  • Reportes e indicadores del inventario y del uso del sistema.

6. Flujo general de uso

  1. El usuario accede al portal mediante correo institucional y contraseña.
  2. Si es un usuario nuevo, crea su cuenta y, en caso de estudiante, adjunta su boleta en formato PDF.
  3. El personal encargado revisa el estado del usuario y valida la documentación cuando corresponde.
  4. Una vez habilitado, el usuario puede consultar inventario y generar solicitudes.
  5. La solicitud pasa por estados de control hasta concluir con entrega, devolución, rechazo, cancelación o penalización.
  6. El sistema registra cambios, estados y datos necesarios para consulta posterior, estadísticas y auditoría.

7. Acceso al sistema

7.1 Inicio de sesión

La pantalla de acceso solicita correo institucional y contraseña. El sistema fue diseñado para usar cuentas vinculadas a dominios institucionales de la UTN. Una vez autenticado, el usuario es redirigido a su panel o módulo correspondiente, según el rol que posea en su registro.

Durante el acceso, el sistema también utiliza información guardada en sesión local para mantener el nombre del usuario, el rol, el token de autenticación y su contexto de navegación.

7.2 Cambio de contraseña

Desde la pantalla de acceso existe una opción de cambio de contraseña. Esta funcionalidad es importante para la continuidad operativa, ya que reduce dependencia del soporte técnico cuando un usuario olvida o necesita renovar su clave. La contraseña debe respetar la política implementada en el sistema, que exige una longitud mínima de ocho caracteres.

7.3 Restricciones de acceso

El sistema no permite el uso libre de cualquier correo. La validación actual acepta correos de la UTN y, en varios procesos, condiciona el acceso al estado del usuario. Por ejemplo, un usuario sancionado, inactivo o pendiente de devolución puede quedar impedido para crear nuevas solicitudes.

8. Registro de usuarios y validación documental

8.1 Información básica del usuario

Cada usuario del sistema maneja, entre otros, los siguientes campos relevantes: cédula, nombre completo, correo electrónico, contraseña cifrada, rol, permisos, estado del usuario y fecha del último acceso. Para estudiantes, también se contemplan datos académicos como código estudiantil, carrera, cuatrimestre, estado de matrícula y referencias asociadas a la boleta.

8.2 Reglas de registro

  • La cédula debe contener solo dígitos y una longitud compatible con la validación del sistema.
  • El correo debe pertenecer a dominios institucionales permitidos.
  • La contraseña debe tener al menos ocho caracteres.
  • El rol inicial puede variar, pero el sistema distingue entre estudiante, docente, administrativo, operador y admin.

8.3 Gestión de boletas

Para estudiantes, el sistema maneja una lógica formal de boletas PDF. El documento puede estar en los estados pendiente_boleta, pendiente_revision, validada o rechazada. Esta funcionalidad se relaciona directamente con la gestión del cuatrimestre activo y con los requisitos institucionales para permitir solicitudes.

La boleta queda almacenada como archivo en el servidor y se registran además observaciones, fecha de carga, periodo asociado y validación administrativa.

8.4 Revisión administrativa de boletas

Desde el módulo de gestión de cuatrimestre, el personal encargado puede visualizar las boletas pendientes y tomar una decisión. Al aprobar una boleta, el sistema la marca como válida; al rechazarla, conserva el registro y exige la carga de un nuevo documento o la corrección del problema señalado en observaciones.

9. Gestión de cuatrimestre

El módulo de cuatrimestre cumple una función crítica en la operación del sistema, porque define el periodo académico activo y determina si se requiere una nueva boleta estudiantil. Cada cuatrimestre se registra con código, fecha de inicio, fecha de fin, indicador de activación y observaciones administrativas.

Al activar un nuevo cuatrimestre, el sistema reinicia la necesidad de boleta para estudiantes, dejando sus registros en estado de revisión requerida. Esto garantiza que el control documental permanezca alineado con el ciclo académico vigente.

Elemento Uso
Código del cuatrimestre Identifica formalmente el periodo activo, por ejemplo un código interno académico.
Fecha de inicio Marca la apertura del periodo y ayuda a determinar si está vigente, futuro o vencido.
Fecha de fin Define el cierre del periodo y el límite de su ventana de vigencia.
Requiere boleta Controla si el sistema exige validación documental al estudiantado.
Boletas pendientes Permite aprobar o rechazar documentos de manera centralizada.
Importancia operativa: la configuración del cuatrimestre no es un paso decorativo. Afecta directamente la elegibilidad de los estudiantes, el control documental y la consistencia del proceso de préstamo.

10. Gestión de activos

Los activos corresponden a bienes identificables individualmente, tales como instrumentos y herramientas. Cada activo posee identidad propia, por lo que se registra con número de activo, número de serie, marca, modelo, categoría, características, observaciones e imagen.

10.1 Categorías de activos

  • Instrumentos
  • Herramientas

10.2 Estados de activos

  • Disponible
  • Prestado
  • En espera
  • Fuera de stock
  • Eliminado
  • Fuera de servicio

10.3 Operaciones disponibles

  • Registrar un activo nuevo de forma individual.
  • Registrar activos de forma masiva.
  • Editar la información de un activo existente.
  • Buscar por texto, marca, modelo o características.
  • Filtrar por categoría o por estado.
  • Asociar imágenes de manera manual o masiva.
  • Marcar activos en mal estado o fuera de servicio.
  • Dar de baja lógica, manteniendo la trazabilidad histórica.
  • Exportar información y generar reporte HTML de activos.

10.4 Reglas de control

El sistema exige unicidad para el número de activo y el número de serie, lo que evita duplicidad de registros. La baja de un activo no lo elimina físicamente del historial; más bien cambia su estado a eliminado y registra observación, fecha de baja y usuario responsable. Este enfoque es apropiado para auditoría y control institucional.

10.5 Uso recomendado por encargados

El módulo debe ser utilizado como registro maestro de cada equipo del laboratorio. Si un activo sufre daño, sale de uso o entra en proceso de reparación, el cambio debe reflejarse de inmediato en el sistema para evitar solicitudes erróneas y para mantener confiables los reportes de disponibilidad.

11. Gestión de insumos

Los insumos son materiales consumibles o unidades que se administran por cantidad. A diferencia de los activos, no se controlan uno a uno por serie, sino por stock disponible, categoría, ubicación y movimientos registrados.

11.1 Campos relevantes del insumo

  • ID interno del insumo.
  • Código único.
  • Tipo.
  • Nombre del producto.
  • Cantidad.
  • Características.
  • Categoría.
  • Ubicación.
  • Estado.
  • Imagen.
  • Movimientos de trazabilidad.

11.2 Categorías de insumos

  • Componentes Analógicos
  • Componentes Digitales

11.3 Estados de insumos

  • Disponible
  • Prestado
  • En espera
  • Fuera de stock
  • Eliminado
  • Fuera de servicio

11.4 Trazabilidad de movimientos

Una característica importante del módulo es el historial de movimientos. Cada edición o ajuste relevante puede registrar tipo de movimiento, cantidad anterior, cantidad nueva, estado anterior, estado nuevo, observación, usuario y fecha. Esto facilita control interno y permite explicar por qué cambió la existencia de un producto.

11.5 Reglas automáticas de stock

El sistema normaliza de forma automática el estado del insumo según la cantidad disponible. Si la cantidad llega a cero, el estado puede pasar a fuera de stock. Si existe disponibilidad y el estado no corresponde a una excepción como eliminado o en espera, el sistema lo considera disponible.

11.6 Utilidad para encargados

Este módulo debe reflejar la realidad física del laboratorio. Su valor no está solamente en saber cuántos insumos existen, sino en permitir prevenir quiebres de stock, detectar materiales críticos y respaldar la planificación de reposiciones.

12. Solicitudes de préstamo

El módulo de solicitudes es el centro operativo del sistema. Aquí se enlazan usuarios, activos e insumos en una misma transacción funcional, permitiendo gestionar desde la petición inicial hasta la devolución o cierre del caso.

12.1 Qué puede incluir una solicitud

  • Uno o varios activos.
  • Uno o varios insumos con cantidad específica.
  • Observaciones del solicitante.

12.2 Reglas de negocio observadas en el sistema

  1. El usuario que crea la solicitud se obtiene desde la sesión autenticada, no desde un dato libre del formulario.
  2. Un usuario en estado inactivo, sancionado o pendiente de devolución no puede crear nuevas solicitudes.
  3. Si el usuario ya tiene una solicitud pendiente, el sistema bloquea la creación de otra nueva en ese estado.
  4. Los activos solo entran a la solicitud si están disponibles.
  5. Los insumos solo entran a la solicitud si existe stock suficiente.
  6. Si un recurso no está disponible, el sistema puede mover al usuario a lista de espera en lugar de aprobar automáticamente el requerimiento.

12.3 Estados de una solicitud

  • Pendiente
  • Aprobada
  • Rechazada
  • Entregado
  • Penalizado
  • Devuelto
  • Cancelada

12.4 Historial de estados

Cada solicitud conserva un histórico cronológico de cambios de estado. Esto permite saber cuándo fue creada, aprobada, rechazada, devuelta o penalizada, así como las observaciones asociadas a esos cambios. Para estados críticos como rechazo, devolución o penalización, el sistema contempla la necesidad de observaciones, lo cual fortalece la trazabilidad administrativa.

12.5 Fechas relevantes en el flujo

  • Fecha de préstamo.
  • Fecha de entrega esperada.
  • Fecha de devolución real.
  • Fecha programada de recogida.
  • Hora de recogida.

12.6 Recomendación operativa

Las personas encargadas deben revisar constantemente las solicitudes pendientes y mantener los estados al día. Un estado incorrecto afecta la disponibilidad del inventario, la experiencia del usuario y la veracidad de los reportes.

13. Lista de espera

La lista de espera permite atender situaciones en las que un activo o insumo no está disponible al momento de la solicitud. En vez de perder el requerimiento, el sistema conserva la intención de uso y asocia al usuario con el recurso solicitado bajo estado de espera.

Esto es especialmente útil para recursos con alta demanda o existencia limitada. Desde el punto de vista institucional, la lista de espera aporta visibilidad sobre necesidades insatisfechas, lo cual puede orientar compras, redistribución de inventario o ajustes operativos.

14. Perfil del usuario y seguimiento personal

El sistema cuenta con un módulo de perfil donde el usuario puede consultar sus datos principales, revisar sus préstamos activos y ver el comportamiento de sus solicitudes. Esta vista es importante porque reduce consultas manuales al personal encargado y fomenta el autocontrol del usuario sobre su situación dentro del sistema.

El perfil también ayuda a identificar si una persona mantiene préstamos pendientes, si posee restricciones o si necesita completar documentación para operar normalmente.

15. Notificaciones

Existe una vista de notificaciones que centraliza eventos relevantes del usuario, como pendientes administrativos, movimientos relacionados con solicitudes o referencias a lista de espera. En términos operativos, este módulo contribuye a reducir la desinformación y favorece que el usuario responda a tiempo ante un requerimiento institucional.

16. Gestión de usuarios

El módulo de gestión de usuarios es una herramienta administrativa para control de cuentas, roles y accesos. Su función no se limita a aprobar usuarios, sino que permite aplicar gobernanza sobre quién puede entrar al sistema y qué puede hacer dentro de él.

16.1 Funcionalidades principales

  • Buscar usuarios por nombre, cédula o correo.
  • Filtrar por rol.
  • Modificar rol y estado de la cuenta.
  • Asignar permisos específicos a operadores.
  • Revisar docentes pendientes de aprobación.
  • Actualizar estado de docentes mediante archivo CSV.
  • Inactivar usuarios.
  • Sancionar y levantar sanciones.
  • Ejecutar acciones de mantenimiento de cierre de cuatrimestre.

16.2 Permisos personalizados para operadores

El sistema contempla permisos específicos para el rol operador. Esto permite crear perfiles intermedios sin necesidad de entregar control total. Los permisos observados incluyen inventario, solicitudes, reportes y usuarios. Este diseño es adecuado para segmentar funciones y reducir riesgo de cambios indebidos.

16.3 Control de docentes por CSV

La interfaz administrativa incluye una función de actualización por CSV para docentes. El formato esperado contempla nombre completo, cédula, correo y estado. Esta capacidad es útil cuando la institución maneja listados oficiales externos y necesita reflejar de forma rápida el estado de cuentas docentes en el sistema.

17. Reportes y estadísticas

El módulo de reportes presenta un enfoque de análisis que combina indicadores, filtros por periodo, tablas y gráficos. El encargado puede generar vistas generales o enfocadas en activos, insumos, usuarios o movimientos.

17.1 Indicadores incluidos

  • Total de activos.
  • Total de insumos.
  • Solicitudes del mes.
  • Usuarios activos.
  • Alertas de stock bajo.
  • Movimientos recientes.
  • Items críticos o fuera de servicio.

17.2 Utilidad institucional de los reportes

Los reportes permiten ver tendencias de uso, saturación de inventario, comportamiento por categoría y activos más solicitados. No se trata solo de una visualización gráfica; este módulo puede servir para justificar reposiciones, medir carga operativa y respaldar decisiones sobre mantenimiento o adquisición de recursos.

18. Resumen del inventario

El sistema también dispone de un módulo de resumen de inventario con KPIs específicos sobre disponibilidad, préstamos, categorías, stock y activos fuera de servicio. Este módulo funciona como panel ejecutivo para obtener una visión rápida del estado general del laboratorio.

19. Reglas institucionales y controles automáticos

Regla Descripción operativa

Bloqueo por estado del usuario Usuarios sancionados, inactivos o con pendientes de devolución no pueden operar con normalidad.
Unicidad de registros clave Evita duplicidad en cédulas, correos, códigos de insumo, números de activo y números de serie.

20. Especificaciones funcionales del sistema

20.1 Especificación de usuarios

El sistema almacena la identidad del usuario, su tipo de rol, permisos, estado, datos académicos y datos documentales. La autenticación se basa en credenciales y token de sesión. El modelo contempla control de sanciones, estados de matrícula, historial de boleta y último acceso.

20.2 Especificación de activos

Cada activo es una entidad individual con identificación única, categoría predefinida y estado controlado. Puede incluir imagen, observaciones y rastreo de disponibilidad para integrarse con el módulo de solicitudes.

20.3 Especificación de insumos

Cada insumo mantiene stock, código único, categoría, ubicación, estado y bitácora de movimientos. La lógica del sistema ajusta su estado según cantidad y según acciones administrativas o de préstamo.

20.4 Especificación de solicitudes

La solicitud es una entidad relacional que conecta usuario, activos e insumos con un folio secuencial. Conserva fechas, observaciones, estados, comentarios administrativos e histórico de eventos. El folio se genera automáticamente para facilitar el seguimiento.

20.5 Especificación de cuatrimestre

El cuatrimestre activo se maneja como configuración del sistema. Solo uno debe estar activo a la vez. Su registro influye en la validación documental del estudiantado y en el comportamiento de módulos académicos.

21.2 Consideraciones de infraestructura

El sistema ha sido preparado para ejecutarse de manera local y también mediante contenedores. En el entorno revisado se utilizan Node.js, npm, MongoDB, Docker Compose, Podman y ngrok como herramientas de soporte. La documentación existente del proyecto también contempla comandos de arranque, reinicio y exposición del frontend cuando se necesita acceso remoto controlado.

Para el funcionamiento actual del sistema se ha utilizado un dominio temporal de ngrok con el fin de exponer el servicio de forma controlada durante las pruebas y el acceso remoto. Esta configuración debe entenderse como operativa y temporal, por lo que conviene revisarla periódicamente si el dominio cambia o si se reemplaza por una solución institucional definitiva.

21.4 Ajuste futuro al dominio real

Cuando el sistema deje de utilizar el dominio temporal de ngrok y pase a operar bajo un dominio real o institucional, no basta con anunciar el nuevo enlace de acceso: es necesario guardar el cambio explícitamente en los archivos de configuración que hoy controlan el acceso externo, los hosts permitidos y la política de origen del backend.

En otras palabras, el nuevo dominio debe quedar escrito y guardado en los archivos del proyecto, para que el sistema reconozca correctamente desde qué dirección se está accediendo.

Archivo Ruta exacta Qué debe ajustarse
Configuración CORS del backend backend/src/app.js En la lista origin debe reemplazarse o agregarse el nuevo dominio real para permitir peticiones válidas desde ese sitio.
Hosts permitidos del frontend en Vite frontend/vite.config.js En la propiedad allowedHosts debe sustituirse el dominio de ngrok por el dominio definitivo, o agregarse el nuevo host según corresponda.
Proxy y acceso local del frontend frontend/vite.config.js Debe revisarse también la configuración de proxy si la arquitectura de publicación cambia al moverse desde ngrok hacia un dominio propio.
Variables del contenedor frontend docker-compose.yml y docker-compose-portainer.yml Conviene revisar los valores de VITE_API_URL y VITE_API_PROXY_TARGET para asegurar que sigan apuntando al backend correcto bajo el nuevo escenario.
Proxy web institucional, si se usa Caddyfile Si el dominio real se atiende mediante Caddy u otro proxy, aquí debe guardarse la nueva relación entre dominio público y servicios internos.
Resumen práctico: cuando se ajuste el dominio real, el cambio debe quedar guardado principalmente en backend/src/app.js y frontend/vite.config.js. Si además el despliegue depende de contenedores o de un proxy web, también debe verificarse y guardarse en docker-compose.yml, docker-compose-portainer.yml y, si aplica, en el Caddyfile.

Después de guardar estos cambios, se debe reiniciar o reconstruir el entorno para que la modificación tome efecto. En el contexto actual del proyecto, esto normalmente implica levantar nuevamente los contenedores del sistema.

22. Recomendaciones de uso para encargados

  1. Actualizar estados de solicitudes el mismo día en que ocurra la entrega, devolución o rechazo.
  2. Registrar daños o salidas de servicio en cuanto se detecten.
  3. Revisar periódicamente boletas pendientes y docentes sin aprobar.
  4. Usar observaciones claras y completas en sanciones, rechazos y bajas.
  5. Respaldar la integridad del inventario verificando que la información del sistema coincida con el inventario físico.
  6. Monitorear reportes de stock crítico para anticipar faltantes.

23. Riesgos operativos si no se usa correctamente

  • Préstamos registrados con estados incorrectos pueden aparentar disponibilidad falsa.
  • Boletas no revisadas a tiempo pueden bloquear usuarios válidos o habilitar usuarios sin respaldo documental suficiente.
  • Un inventario desactualizado reduce la confiabilidad institucional del sistema.
  • La omisión de observaciones limita la trazabilidad ante incidencias o auditorías.
  • Una mala asignación de permisos puede exponer módulos sensibles a usuarios no autorizados.

24. Procedimientos sugeridos por perfil encargado

24.1 Encargado de laboratorio

Debe concentrarse en la verificación del inventario físico, la actualización de estados de activos e insumos y el seguimiento de solicitudes activas. También debe utilizar la lista de espera como señal de demanda no cubierta.

24.2 Encargado administrativo

Debe velar por la consistencia de usuarios, boletas, solicitudes, reportes y control documental. Este perfil puede usar el sistema para supervisar el orden del proceso y respaldar decisiones operativas.

24.3 Administrador del sistema

Debe controlar configuraciones críticas, roles, sanciones, mantenimiento funcional y cambios estructurales del periodo académico. Además, le corresponde corregir situaciones excepcionales que el usuario final no puede resolver por sí mismo.

25. Conclusión

SPIEE no es únicamente una interfaz para pedir materiales; es una plataforma de control institucional que integra inventario, préstamos, usuarios, documentación académica y supervisión administrativa. Su utilidad depende directamente de que la información ingresada y los estados mantenidos reflejen la realidad operativa del laboratorio.

Si se utiliza de forma disciplinada, el sistema permite mejorar trazabilidad, transparencia, orden documental y capacidad de respuesta. Por ello, se recomienda que este manual sea compartido con las personas encargadas y que sirva como base para capacitaciones, lineamientos internos y futuras mejoras del sistema.
